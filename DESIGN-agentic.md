# Agentic career-ops — design for Staff review

Status: proposed; implementation and live execution have not started.
Scope: BUI-196; base 0fbb8487b28ae6a097568cc1ab81b6adf507c574.

## Why / runtime decision
Keep collectors, dedupe, timers, SQLite graph edges and all final safety gates deterministic. Replace model-step scripting with a bounded Career Ops team launched by the Python pipeline: evaluator/researcher, drafter/reviser (`openai/sol`), and fresh-context reviewer (`openai/astra`). Each worker uses a small tool-selection loop over the existing OmniRoute client; tools are explicit Python functions, not shell commands. No Pi CLI dependency, new service, Paperclip runtime issues per posting, agent hiring or Paperclip agent changes.

Compared options: Paperclip per-batch agents add control-plane coupling and put candidate material in issue contexts; Pi subprocesses add a second provider/configuration and tool-permission boundary. Embedded pipeline-launched workers reuse `jobwatch.llm`, enforce paid routes in one place, and provide genuine bounded tool choice instead of simply renaming fixed calls. Paperclip remains the build/review control plane. This also respects GOAL_CONTRACT's prohibition on touching Paperclip agents.

## Work and tools
Evaluator sees the full captured advert, not title/snippet, and first produces JD-only requirement importance before candidate evidence is supplied. Then it reads `career_ops_profile.md`, CV and existing evidence from the read-only profile directory. It may request bounded employer/compensation research when needed, without transmitting candidate data to search/fetch providers. Output: archetype, quoted requirement-to-evidence matches and gaps, work-rights facts, five rubric dimensions, holistic 1–5 global score, legitimacy tier and cited observations, tailoring brief. Owner career targets replace the archived AI-role archetypes.

Drafter chooses relevant evidence and tailoring angles, writes structured CV/letter content and screening answers; it cannot invent identity, experience, salary expectations or availability. Reviewer receives a fresh context containing JD, cited evidence, rubric result and draft; returns approve or specific revisions. At most one revision cycle. Agent loops expose only read-JD, read-profile/evidence, bounded public research, structured draft submission and review submission. No shell, arbitrary filesystem, browser actions, nested agents, email, submit, or direct DB writes.

Research: at most five queries and three safe fetched pages per job, cache by employer and query with timestamp, only employer/role context leaves the machine. Validate URLs/redirects; block local/private addresses and credential-bearing URLs. If usable search access is absent, record research unavailable; never fabricate findings. Contradictory identity/liveness or suspicious legitimacy holds drafting; missing salary alone does not. Actual endpoint/library choice belongs to Plan after installed-access inspection, not a new paid subscription.

## Rubric adaptation (explicit, not blind archive restoration)
References are extracted verbatim into `.planning/phases/01-agentic-career-ops/reference/` from Drive's `job-system-20261004.tar`, paths `workspace/job-tracker/career-ops/modes/{oferta,_shared}.md` under the tar's `job-system-20261004/` root. No archived code or data service is restored.

Preserve: full-ad archive; two-pass requirement importance; inferred requirements cannot be critical/high or blockers; exact primary-file evidence; honest gaps; bounded inline research; holistic CV match/North Star/comp/culture/red-flags judgment; legitimacy separate from score; warnings describe observations, never accusations. Compact A–G evaluation and H screening map remain available alongside PDFs. Never turn unsupported unknowns into positive evidence.

Do not apply the archive's senior-AI positioning, default archetypes, shell scripts, tracker TSVs, personal file layout, contact discovery, persistent profile/story-bank writes, or interactive questions. Agency uncertainty is a per-job hold with recorded evidence and no draft, not a question to the owner or a guessed end employer. Legal signals requiring missing jurisdiction tables are marked not evaluated; no invented legal advice. Screening maps are prepared for eligible jobs regardless of the archive's 4.5-only H default, because jobwatch's apply contract requires them.

The archive's holistic score differs from current `MatchScore.overall` (40/30/30 arithmetic). Agentic mode needs a separately versioned typed evaluation/global score; do NOT disguise a holistic score as legacy component marks. Share hard-gate logic through a narrow adapter taking score + quoted facts, retain legacy scoring unchanged when the flag is off. Agentic auto-draft eligibility is >=4.0, matching GOAL_CONTRACT T28, not the unapproved 3.8 legacy default. Owner targets and work-rights/location/hours/program restrictions always outrank model judgment.

## State / artifacts / board
`pipeline.agentic.enabled` defaults false. Flag off preserves old path. Flag on uses agent evaluation at extract/evaluate and agent drafting at draft, retaining `draft_queued -> drafted -> form_map -> ready`; code alone controls graph transitions. Already-queued jobs MUST be freshly evaluated and re-gated under the new rubric before drafting. Persist that re-evaluation under a versioned agentic sidecar/event without illegal reverse graph moves; nonqualifying jobs are held out of drafting with a visible reason via an explicit, tested graph extension if required. Never force a gate-failed job ready to achieve a quota.

Use existing application/draft rows, append-only ledger and `drafts/<application>/v<n>/`; no direct worker persistence. Adapter validates outputs, claim citations, reviewer acceptance, deterministic gate and `verify_pdf`, then writes with the existing ledger API. Store full ad, rubric version, profile/content hashes, sanitized tool audit, reviewer verdict and verify reports in private data files. Job content/evidence/form answers never enter git, issue attachments or service logs. Pipeline actor events must identify automation, not falsely record an owner command.

Resume key: posting + ad hash + profile hash + rubric version. Lease/claim a job before work; persist completed checkpoints and reuse verified output on restart. Transactional stage commit/CAS and lease expiry prevent duplicate workers; failure after render/ledger write must reconcile, not blindly create another version. Board shows queue/in-progress/reviewing/held/failed/ready counts and per-job reason, verified PDFs, fit/gaps, form-map unknown count and provenance. READY means prepared for owner review/manual submission, not form filled or submitted.

## Limits / failure handling
[default] two jobs in flight; batches of 20, then repeat over the snapshot of the reported 126 queued posting IDs. Reconcile actual count at execution; historical 126 is not a live invariant. At most eight worker tool/model turns per role, one revision, 15 minutes/job and a 30-minute batch deadline; no new work starts after deadline. Enforce aggregate input+output token budget (100,000/job; 2,000,000/20-job batch), including retries and review. These are safety ceilings, not promised consumption. Keep old 10/day guard for legacy mode; explicit agentic batch limit replaces it only for approved flagged execution. Record tokens and API-equivalent cost separately from actual subscription spend. No paid fallback when the ChatGPT plan/route expires: pause and report route unavailable. Any new spend requires board approval.

Invalid JSON, unsupported claims, tool violations or exhausted budget fail closed. Bounded transient retries share the same deadline/token budget; rate limiting opens a batch circuit breaker. Three failed attempts maximum, including transport/schema retries; no multiplicative graph/agent retry explosion. DLQ holds preserve diagnostic metadata; no blanket recovery or touching unrelated DLQ jobs (especially 144/145). Turning flag off stops admission; existing in-flight work finishes or expires safely. Rollback does not delete ledger or verified drafts.

## Delivery gates / observable acceptance
1. Staff Reviewer approves this design before implementation; Eng Manager writes fresh-context plans and obtains plan check.
2. Synthetic tests prove actual tool choice, full-ad inputs, evidence isolation, route allowlist, hard gates, 4.0 threshold, review rejection, unknown answers, prompt-injection resistance, exhausted budget, restart/idempotency and flag-off compatibility.
3. Full `.venv/bin/python -m pytest -q` passes in the candidate checkout.
4. After board-authorized merge/restart and live data execution, process the queued snapshot in bounded batches. At least 20 genuinely qualifying real jobs have agentic evaluations, accepted reviews, tailored CV + letter, passing `verify_pdf`, form maps and READY board entries. If fewer qualify, report the shortfall; do not waive gates.
5. Board HTTP 200 plus real authenticated/local page walkthrough confirms ready packages and held/failed states. No application submission, employer contact or external form typing in this phase; T19 remains independently owned.
6. Update TRACK section 0, local todo and WHAT-HAPPENED with counts, remaining limitations and undo. Contract remains byte-identical.

What still doesn't work: no agentic runtime yet; archived rubric adoption, agentic scoring, leased/resumable execution and board progress need implementation. Existing form filling and unanswered personal fields are not solved here. Live batch, 20-job verification, merge/restart and spend changes require the downstream checks/approvals, not this design.
