## Feasibility finding: exact approval cannot bridge asynchronous approval

Existing approval binds a **particular manifest hash**. Any DB write after inspect changes the whole-database snapshot and makes apply refuse. Holding SQLite writer transaction across reviewer/board latency is prohibited and unsafe. Thus inspect → release exclusion → request approval → apply cannot promise eventual executability. Approval must not bind speculative manifest, waive whole-snapshot comparison, or refresh manifest under old approval.

A single bounded approved maintenance window is the only compatible direction: board approval in advance for narrowly defined actions/limits, then operator enters window, freshly establishes exclusion, inspects, manifests, backs up and executes only if existing approval binds that exact fresh manifest. Current API/contract cannot bind an unknown future hash nor encode/enforce all operational scope. No second card while paused is acceptable. Thus present tool/governance do not provide an executable same-window sequence; this is incompatibility, not authority to relax guards.

## Concrete boundary proposal (not implemented / not operational)

[Default] The viable code-level direction is a centrally enforced maintenance gate at **every** DB open/write boundary plus OS-level containment for bypasses: wrap `dbm.connect`, replace direct web SQLite opening, and route guarded scripts through the same gate; require process identity/access controls that prevent same-UID raw opens during the lease. Gate grants only the approved maintenance process the write lease, rejects new writers, drains/rejects in-flight requests, and must attest a closed set of processes/open handles. Inventory known calls above; tests and static search are not proof of full coverage. Since standalone raw SQLite clients can bypass an in-process gate, if OS-level enforcement or complete entrypoint coverage cannot be demonstrated, refuse. Unknown PID, executable, open handle, in-flight web request/thread, unregistered entrypoint or bypassed gate => fail closed. Never kill agents/processes.

Current system has no demonstrated gate, dedicated DB identity/ACL boundary, or proof that all same-UID processes honor a gate. So this proposal does **not** create current enforceability. Scheduled-unit stop alone is insufficient. Do not perform operations under this proposal absent future implementation/review and specific board authorization.

## Bounded sequencing and restore semantics

Future offline implementation must use a monotonic 120s deadline from first exclusion through release and reserve cleanup time (prototype default 20s). Before touching units: record each of nine exact ActiveState/SubState and UnitFileState; reject unknown/drop-in/effective definition drift, active one-shot service, unknown/in-flight writer, incomplete access coverage, inability to identify DB identity, or insufficient budget. Active one-shots are never stopped/restarted to restore `active` because restarting re-executes job; refuse before any stop. Inactive oneshots stay inactive. If any other initially active unit is stopped, journal only after successful stop; finally restart only journaled initially-active non-oneshots, never start units initially inactive, and do not change enabled/static/masked/disabled file state. Gate is released in finally. Verify each restoration and report cleanup failure; inability to restore or release gate is critical abort/escalation, not success. No process killing. No timer triggering.

Any timeout, failed stop, drift, manifest/approval mismatch, backup failure or cleanup issue aborts. Durable backup must be private directory 0700/file 0600, exclusive-create and durable before updates. Rollback only exact guarded procedure with separate rollback binding, exact original backup and unchanged full postimage/identity. Intervening write means refuse; never replace whole DB or overwrite later writes.
