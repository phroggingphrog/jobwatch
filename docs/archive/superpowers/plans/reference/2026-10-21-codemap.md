### 0.1 Cross-plan hazards (read first)
1. Run-key churn costs money: `RunKey.config_hash` hashes the whole `_config()` dict, the `TargetPolicy`, `IMPLEMENTATION_VERSION`,
   `LOCATION_REFERENCE_HASH` and the posting identity (`service.py:149-159`). Adding a config key, changing policy contents or bumping the
   version makes every old run stale and every job re-runs its three paid model roles. Gate-only changes do not change the key but DO
   silently re-apply to stored evaluations (see 1.3.3).
2. The gate decision is not stored and `decide()` reads live profile files; `preference_service.pool` calls it without `commute_km`. Any
   "baseline route" must be recomputed under a pinned profile copy and a recorded gate-source hash (6a).
3. The profile projection is lossy (2.2). The decision policy, shortlist labels and exclusion rules must read `approved.json` facts, not
   `profile.yaml`/`interests_and_criteria.yaml`; employment status and locations never reach the old readers, free-text exclusions are not
   enforced in agentic mode, and `gate.py:302-308` still hard-codes interstate cities for every person.
4. Eligible-but-unprepared jobs are stored as `held / evaluation_complete / stage dlq` and are re-queued by `after_collect` each run (they
   re-run `decide` on saved artifacts, no model cost, but a public liveness fetch each time and they consume `daily_assessments`). A shortlist
   needs its own entity or a careful view over `agentic_runs`+artifacts.
5. Preference model data is immutable and version-hashed: editing any of 5 files under `jobwatch/preferences/` invalidates all answered
   sets (3.4/4.4). R/JAGS is not installed here or in CI, so sampler changes cannot be verified without adding the toolchain.
6. Stored JSON models are `StrictFrozen` (extra keys rejected) and hashed; schema changes must be additive with historical-omitting
   serializers, and `location_fit: 'melbourne'` is baked into stored evaluations, prompts and ~20 test occurrences in 10 files.
7. Two embedding paths exist: the approved counted `PaidGatewayEmbeddings` and the legacy uncounted `openrouter_extras.embed` (timer path:
   near-duplicates and `_target_first`). Plan 3 should converge on the approved one.
8. Collection (`matches`, title keywords, `rules.yaml` arms, `searches.yaml`, VIC regexes) is owner-specific config and still feeds callback
   arms and the web `matches` scope; Plan 2/3 must decide whether these stay as a recall-only pre-screen.
9. Tests bake the owner in via autouse fixtures (`tests/conftest.py:137,145`); per-person tests need explicit overrides. The full suite is
   ~2,600 tests and slow; this container needs a venv outside the repo (7.10).

### 1.3 Gaps/hazards specific to freezing (these will bite a plan writer)
1. `decide()` is impure: it reads the live profile through `candidate/person.py` (`hours_limit_per_fortnight` `:36`, `full_time_programs_ok`
   `:47`, `excluded_families` `:57` read `profile.yaml`/`interests_and_criteria.yaml` from `apply.paths.profile_dir()` per call;
   `gate.py:73,113,316`), through `pipeline/agentic/location.py` (`_state()` -> `place.person_state()` -> `apply/render.py:27 _candidate()`
   reads `profile.yaml`; `location.py:23-27,57,139`), and via `commute_km`. A frozen replay must pin `JOBWATCH_PROFILE_DIR` (and
   `users.use(person)`) to a copy of the profile files, and must store `commute_km` (live path passes `km_from_home(posting['location'])`,
   `service.py:457`; `preference_service.pool` passes none, `:39-42`, so pool decisions can differ from live decisions).
2. Gate inputs not in any hash: `interests_and_criteria.yaml` (`excluded_families`) only enters `RunKey.config_hash` indirectly via
   `policy.model_dump()` (`service.py:157`); `profile.yaml` work-rights limits enter via the evidence bundle (profile.yaml is in `_ALLOWED`)
   but gate reads them live, not from the bundle.
3. Gate code revisions do not change run keys; only `IMPLEMENTATION_VERSION` (`service.py:48`), `RUBRIC_VERSION` (`:44`),
   `LOCATION_REFERENCE_HASH` (`location.py:18`), policy, cfg and `posting` identity do (`_run_key` `:149-159`; tests
   `test_agentic_service.py:606,617`). Consequence: `run_agentic_job` (`:333-337`) returns early (stays ARCHIVED, no re-check) for a
   previous archive of the same run_key whose reason is NOT in `{posting_closed, score_below_threshold, hard_gate}`; archives with one of
   those three reasons fall through and, via `:447-457`, re-run `decide` on the saved `evaluation` artifact with today's gate and today's
   profile files (the comment at `:333` says an owner rule change must apply to jobs already judged). Holds and `evaluation_complete` runs
   always re-run `decide` the same way. So a frozen baseline must record the gate
   source hash (file sha of `gate.py`, `location.py`, `person.py`, `reader.py` rights regexes) next to each stored route, or old routes
   cannot be told apart from re-applied ones.
4. Bumping `IMPLEMENTATION_VERSION` (needed whenever extraction/matching prompts change) changes every `run_key` -> all jobs re-evaluate
   with paid model calls. Plans 2/3/4 each tempt this. Gate-only policy changes (Plan 2) can avoid it only if `TargetPolicy`/`cfg` stay
   byte-identical.
5. The evaluator is stochastic; `evaluate_job` saved per run_key in `evaluation` artifact is the only frozen model output. Freeze from
   artifacts (`agentic_artifacts` rows + files), not by re-running. Baseline "inputs" = `snapshot` + `structural_inputs` artifacts; baseline
   "outputs" = `evaluation` + `candidate` + `model_insights` artifacts + the recomputed `decide()` result.
6. Artifact files live under `users.user_dir(person)/agentic/<run_key>/` and drafts dirs, hash-verified by `_read_artifact`
   (`persistence.py:38`, must be inside `data_dir()`), 0600/0700. Anything written by 6a must go through

7. Never use live candidate data as fixtures (AGENTS.md). All existing synthetic worlds are in `tests/test_agentic_service.py:117 world` and
   `tests/test_agentic_evaluate.py:29 build_case`.
8. Legacy holistic scores also exist for non-agentic modes: `ad_reviews.score/archetype/legitimacy/report_json/model_json` (db.py v8 `:294`)
   and `pipeline_state.data_json` (`pipeline/store.py:14`). Decide explicitly whether 6a freezes them (they feed the board for rows read
